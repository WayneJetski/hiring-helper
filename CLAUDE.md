# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Hiring Helper is a BambooHR applicant-tracking interface. It mirrors BambooHR hiring data into a local SQLite database, and candidate scoring is done by Claude through an **MCP server** that reads that data and writes scores/summaries back (there is no outbound LLM call from the app). npm workspaces monorepo: `client` (React + Vite + TypeScript) and `server` (Express + TypeScript, ESM). The server has two entry points: the REST API (`src/index.ts`) and the MCP stdio server (`src/mcp/index.ts`).

## Commands

Run from the repo root unless noted.

```bash
npm install              # installs root + both workspaces (workspaces are configured)
npm run dev              # runs server (:3000) and client (:5173) together via concurrently
npm run dev:server       # server only, tsx watch
npm run dev:client       # client only, vite
npm run build            # builds client then server (tsc compiles both entry points)
npm start                # runs the built REST server (server/dist/index.js)

npm run mcp --workspace=server     # runs the MCP stdio server (tsx src/mcp/index.ts)
npm run mcp:check --workspace=server   # self-check: starts the server from .mcp.json and lists its tools (needs npm run build)

start.bat                          # Windows one-click launcher for non-developers (see below)

npm run lint --workspace=server    # eslint src --ext .ts
npm run lint --workspace=client    # eslint . --ext ts,tsx (max-warnings 0)
npm run test --workspace=client    # pure client helpers (node --import tsx --test)
```

The MCP server is registered for Claude Code via the project `.mcp.json` (`node --import tsx server/src/mcp/index.ts`, not `npm`, so it also spawns on Windows; `.claude/settings.json` pre-approves it for headless runs). See `MCP.md` for the tool list and scoring workflow.

The Vite dev server proxies `/api` to `http://localhost:3000`, so run both for a working app.

The **server** has a lightweight test setup using Node's built-in runner (no framework dependency): `npm run test --workspace=server` runs `node --import tsx --test "src/**/*.test.ts"`. Tests live next to the code as `*.test.ts` (e.g. `server/src/services/bamboo-push.service.test.ts`) and are excluded from the build via `tsconfig` `exclude`. The **client** runs only pure-helper tests (no component/DOM tests). The `.cursorrules` mentions Jest and React Testing Library, but that is aspirational.

### Installers, the `hiring-helper` command and updates

Two ways to run it besides `npm run dev`:
- **Zip + `start.bat`** (Windows): foreground, no git; updates are a new zip (see the launcher section above).
- **Installer** (`install.sh` for macOS/Linux, `install.ps1` for Windows; one-liners in the README): asks for folder and port (defaults: per-OS data folder, port **28417**), installs git if missing, `git clone`s `WayneJetski/hiring-helper` (`HH_REPO_URL`/`HH_BRANCH` override, used by CI), writes `PORT` into `.env`, adds `<install>/bin` to PATH (a marked block in the shell profile, or the user PATH on Windows), then runs `hiring-helper start`. Both read answers from the keyboard (`/dev/tty` / `Read-Host`) and fall back to defaults when there is none or `HH_YES=1`. Flags exist for bash; PowerShell uses `HH_*` variables because `irm | iex` cannot take parameters. Wrapped in `main`/`Install-HiringHelper` so a truncated download runs nothing.

**The command** (`bin/hiring-helper` for bash, `bin/hiring-helper.cmd` -> `scripts/launcher/hiring-helper.ps1` for Windows; same commands): `start [--foreground] [--no-open]`, `stop`, `restart`, `status`, `open`, `logs [-f]`, `update [--check]`, `doctor`. `start` runs the prerequisites (`scripts/launcher/setup.sh`, or the `Initialize-*` functions from `start.ps1`, which `hiring-helper.ps1` dot-sources; `start.ps1` only runs its launcher when not dot-sourced), then launches `node server/dist/index.js` in the background with `NODE_ENV=production` and `HIRING_HELPER_MANAGED=1`, recording `.runtime/server.pid` and logging to `.runtime/server.log` (Windows: `server.err.log` too). A pid is trusted only if its command line is `server/dist/index.js`. `restart` runs setup first, so a failed setup leaves the running copy alone. Setup uses `npm ci --include=dev` and unsets `NODE_ENV`: under production mode `npm ci` drops TypeScript and Vite and the build fails, and `npm install` would rewrite `package-lock.json` and dirty the clone. `HH_SKIP_CLAUDE=1` skips Claude Code (CI, headless).

**MCP self-check** (`server/src/mcp/mcp-check.ts`, CLI `mcp-check.cli.ts`, `hiring-helper doctor`): scoring is the only feature that needs the MCP server, and nothing else touches it, so a server that cannot start used to surface only at the first scoring click. The check spawns the exact command in `.mcp.json` from the repo root (as Claude Code does), lists tools, requires `REQUIRED_TOOL_NAMES`, and warns if `.claude/settings.json` does not pre-approve the server. `hiring-helper start` runs it **after** the server is healthy (the MCP server opens the database, so the app's own start-up must run migrations first) and only warns; it is not run from `setup.sh`/`start.ps1`, and the zip + `start.bat` path does not run it (use `npm run mcp:check`). `diagnoseServerLog` turns a `NODE_MODULE_VERSION` crash (two Node.js installs, e.g. nvm plus Homebrew) into advice. CI runs `doctor` in both installer jobs. Tests use `server/src/mcp/test-fixtures/fake-mcp-server.mjs`.

**Update check** (`UpdateService`, `GET /api/update/status[?refresh=1]`, reused for 5 minutes): only for a managed install (`HIRING_HELPER_MANAGED=1`; a developer's checkout never reaches out). It asks the remote for the tip of the branch the install follows (`git ls-remote origin refs/heads/<branch>`, nothing downloaded) and reports an update when that commit is not an ancestor of `HEAD` (`git merge-base --is-ancestor`; "present on disk" is not enough, since a rolled-back update leaves the commit downloaded). `compareUrl` is built for GitHub remotes. The banner (`UpdateBanner`) checks on page load and hourly.

**Applying** (`POST /api/update/apply`, then poll the status; the user always clicks, nothing is automatic): refused if not managed, already updating, scoring is running (`scoring-runtime.ts` shares the instance), or tracked files other than `package-lock.json` are modified (lockfile churn is restored with `git checkout`). Steps: `git pull --ff-only`, `npm ci --include=dev` only if a `package*.json` changed, `npm run build`, write `.runtime/build.stamp` (so the restart does not rebuild), then spawn `bin/hiring-helper restart --no-open` detached; that stops this process and starts a new one, and the page reloads when the new commit answers (`utils/updateProgress.ts`). A failed install or build runs `git reset --hard <previous>`, reinstalls and rebuilds, and reports the compiler error (`summarizeFailure` drops npm boilerplate); the old server keeps running throughout. Child commands get `commandEnvironment` (no `NODE_ENV`, no password prompts). Database migrations run on the next start, with a backup.

**Testing it end to end** (done by hand, since it needs real installs): clone the working tree into a scratch git repo as "origin", run `install.sh` against it with a fake `HOME`, a minimal `PATH` (no Node, so it downloads one) and `HH_SKIP_CLAUDE=1`, commit a release to the scratch origin, then drive `/api/update/*` with curl. Do this after changing any launcher, installer or updater code.

### Continuous integration

`.github/workflows/ci.yml` runs on pushes to `main`/`master` and on pull requests:
- **test**: build, lint and tests (server and client) on Ubuntu with Node 22 and 24 and on Windows with Node 22. The server test script uses a quoted glob, which needs Node 21+, so CI starts at Node 22.
- **launcher** ("Windows scripts parse"): parses `start.ps1`, `hiring-helper.ps1` and `install.ps1` with Windows PowerShell 5.1.
- **installer-unix** / **installer-windows**: run the real installer against the commit under test (`HH_REPO_URL=file://...`, a `ci-install` branch), then start the app, hit `/health` and `/api/update/status`, run `update --check`, and stop it. `HH_SKIP_CLAUDE=1` keeps them unattended.
- **hygiene**: fails if `package-lock.json` points at a non-public registry, if local data or `.env` files are tracked, if the Windows scripts contain non-ASCII characters, if a shell script does not parse (`bash -n`), or if one has lost its executable bit in git.

To reproduce the test job locally: `npm ci && npm run build && npm run lint --workspace=server && npm run lint --workspace=client && npm run test --workspace=server && npm run test --workspace=client`.

### One-click launcher for non-developers (`start.bat`, Windows)

`start.bat` runs `scripts/launcher/start.ps1`, which installs/checks the prerequisites and starts the **built** app as one process: Node (downloaded to `.runtime/node` if the machine lacks an even-numbered LTS >= 20, so better-sqlite3 prebuilds apply), Git for Windows (winget; Claude Code needs Git Bash), Claude Code (official `install.ps1`, plus a one-time sign-in check), `npm install` and `npm run build` when stale, then `node server/dist/index.js` on `PORT` (default 3000) and opens the browser. The REST server serves `client/dist` with an SPA fallback (`utils/client-assets.ts`). The web app redirects every route to `/setup` until BambooHR is connected. Keep `start.ps1` ASCII-only and the `.bat`/`.ps1` files CRLF (`.gitattributes`). Build scripts must stay cross-platform (no `cp`/`rm`; the server build uses a Node one-liner).

### Maintenance scripts (`scripts/`)

One-off operational scripts, not part of the build:
- `*.sh` scripts (e.g. `regenerate-all-summaries.sh`, `backfill-scores.sh`) call the **running** dev server's HTTP API, so start `npm run dev` first.
- `*.ts` scripts (e.g. `regenerate-all-summaries.ts`, migrations) import server modules directly and run via `npx tsx scripts/<name>.ts`. Note they import from `../server/src/...js` with `.js` extensions (see ESM rule below).

## Architecture

### Data flow

```
BambooHR API → BambooHRSyncService → SQLite ─┬─ ApplicantsController → REST → React client
                                             └─ MCP server (stdio) → Claude → save_evaluation
```

Read/assembly logic lives in `ApplicantQueryService` (list, detail, resume text, unscored queue, scoring context) so the REST controller and the MCP tools share one implementation. The controller is thin (HTTP parsing + status codes only). The client never talks to BambooHR. The one exception to "serve from local DB" is resume PDFs, which are always fetched live from BambooHR (they are binary), parsed with `unpdf`, and cached to disk.

### Sync (`bamboohr-sync.service.ts`)

- Runs **automatically on REST-server startup** (`server/src/index.ts` → `startServer`), and on demand via `POST /api/sync` or the `sync_from_bamboohr` MCP tool.
- Incremental by default: uses the last **successful** (`full`/`incremental`) `content_updates` timestamp as BambooHR's `newSince`; failed and rate-limited attempts are logged in the same table but never advance the watermark. A full sync (`force=true`) additionally marks applications `inactive` when they no longer appear in BambooHR (`markInactiveExcept`, per job).
- BambooHR 429s degrade gracefully: the sync records a `rate_limited` entry in `content_updates`, returns 0, and keeps serving cached data instead of throwing.
- **New-job discovery (incremental syncs):** the sync snapshots the job ids it already stores, then backfills every not-yet-stored application of any job id it has never seen (`sync-discovery.ts`). This catches applicants who predate our access to a job, which `newSince` would otherwise skip. It works from the full applications list the sync already fetches for status pulls, so it costs no extra list calls (only detail fetches for the backfilled applications). A job with zero applicants is still not created.
- Sync only ingests; it does **not** score. There is no background scoring worker.

### AI scoring (MCP-driven)

Scoring is done by Claude through the MCP server (`server/src/mcp/`), not by an outbound LLM call. Claude reads a candidate (`get_resume_text`, `get_job_description`), assesses fit, and calls `save_evaluation`, which is the only write path. `EvaluationService.saveEvaluation` validates confidence 0–100 and persists the score to `application_scores` (SQLite) plus the written summary to the disk cache. The `evaluate_candidate` MCP prompt bundles the rubric with the resume, keeping the trusted-rubric / untrusted-candidate-data separation (candidate text is fenced and marked as data). The `/score-candidates` Claude Code skill (`.claude/skills/`) drives the whole flow. See `MCP.md`.

**Per-job scoring criteria (structured, not a raw prompt).** The rubric is a fixed template, `server/prompts/ai-evaluation-system.txt` (safety rules, scoring rules, JSON output format; `{{JOB_TITLE}}`/`{{JOB_DESCRIPTION}}` placeholders), with three generated sections: `{{EVALUATION_FRAMEWORK}}`, `{{RED_FLAGS}}`, `{{FLAGS_TO_PASS}}`. Users edit only a `ScoringConfig` (`server/src/scoring/scoring-config.ts`, pure and tested): weighted evaluation areas (name, points, guidance; points must total exactly 100) and five red-flag toggles (name capitalization, location with a free-text `locale`, studying, no experience, short tenures or gaps); all are on by default except location, which stays off until a job names where it is based (there is no default place). **The model never adjusts its score for a flag** (the rubric says so explicitly); a flag lowers the score only through its configurable penalty, applied by the app (next paragraph). The `tenure` flag (label "Tenure / Gaps") is for a pattern of short roles or unexplained gaps of about six months or more, excluding internships, co-ops, placements and anything described as a contract/freelance/temporary, and gaps the résumé explains; the flag keys are `name`, `location`, `studying`, `no_exp`, `tenure` (plus the answer-derived salary flags, preserved separately). `jobs.scoring_config` holds it as JSON (NULL = defaults, `DEFAULT_SCORING_CONFIG`). `composeRubric` fills the template (and strips `{{`/`}}` from user text so it cannot inject placeholders); the generated "Flags to pass to save_evaluation" list is what the scoring skill follows, so a disabled flag is never set. `JobDescriptionService.getSystemPrompt(jobId)` returns the composed rubric. It reaches scoring two ways: the `evaluate_candidate` MCP prompt (`fillRubric`, interactive), and the **model-callable `get_system_prompt` MCP tool** that the `/score-candidates` skill calls as its authoritative rubric (MCP prompts are not model-invocable inside a headless `claude -p` run). **Legacy:** `jobs.system_prompt` (the old free-text override) is kept as a backup; on startup `convertLegacyRubrics` converts parseable ones (`parseLegacyRubric`) into `scoring_config`. One that cannot be converted keeps being used as written until the user clicks "Switch to guided criteria" (which resets to defaults and clears it). The `location` flag text is generic over `locale`. `parseLegacyRubric` reads the place from the old rule's "based in X" sentence, and keeps the legacy prompt as written when it cannot find one.

**Red-flag penalties.** Each red flag in a job's `ScoringConfig` has a `penalty` (`none` default, `bit` = -5, `lot` = -15, `dealbreaker` = cap at 20), set with a slider in the editor. The model scores on merit and only reports flags; `EvaluationService.saveEvaluation` applies the penalties with the pure `applyFlagPenalties` (`scoring/flag-penalties.ts`) and stores the final score. When a penalty took effect, the summary carries `scoreAdjustment` (merit score and penalties) and the AI card explains it. Configs saved before penalties existed load as `none`. A changed penalty affects only later scoring; use Re-score for existing applicants. Keep the client's `FLAG_PENALTY_LEVELS` (`utils/scoringConfig.ts`) in step with the server numbers.

**Desired-pay flags are app-owned.** `redFlags.salaryLow`/`salaryHigh` (`SalaryFlagSetting`: `enabled`, `penalty`, yearly `threshold`) are off until a threshold is entered. They are not in the rubric: `saveEvaluation` derives `salary-low` (pay below the threshold) and `salary-high` (above) from the stored `applications.desired_salary` with `deriveSalaryFlags` (`scoring/salary.ts`, which also owns `parseSalary`), rewrites the stored salary flags via `reconcileSalaryFlags` (a check that is off leaves existing flags alone), and the same penalty slider applies.

**Claude sign-in from the app (`ClaudeAuthService`).** `GET /api/setup/status` reports `claude.signedIn`/`account`/`isSigningIn` from `claude auth status` (JSON, cached 15 s; unreadable output is `null`/unknown, never "signed out"). `POST /api/setup/claude/signin { sso? }` runs `claude auth login [--sso]` (stdio ignored, one at a time, killed after 5 min; `.../signin/cancel` stops it), which opens the browser on this computer, so it relies on the loopback-only server living on the user's machine. The setup screen polls status while a sign-in is open, and the applicant list shows a banner when Claude is missing or signed out. A Claude result saying "not logged in" is mapped to `NOT_SIGNED_IN_MESSAGE` in both `ScoringService` and `ClaudeRunner`.

**Triggering scoring from the web (`ScoringService`).** A "Score new applicants" button (`POST /api/score`) spawns **headless Claude Code** (`claude -p`) in the repo root, which runs the `/score-candidates` skill against the `hiring-helper` MCP — the app still makes no LLM call and holds no key. The run is sandboxed to `--allowedTools "Skill" "mcp__hiring-helper__*"` (no Bash/Write/Edit), single-flight, pins `--model` (default `claude-sonnet-5-5`, override via the `SCORING_MODEL` env var — capable for rubric scoring and far cheaper/faster than inheriting Opus), and progress is parsed from `--output-format stream-json` (counts `save_evaluation` calls). `GET /api/score/status` is polled by the UI. **Prerequisite:** the Claude Code CLI must be installed + authenticated on the host running the server; scoring spends tokens on that account.

**Job scoping:** candidates belong to a job (`applications.job_id`). `list_applicants`/`list_unscored_applicants` (MCP) and the web list default to the **current job** — `ApplicantQueryService.resolveCurrentJobId()`, the most recent application activity — so different postings aren't mixed. `listJobs()` / `GET /api/jobs` / the `list_jobs` tool enumerate jobs.

**Job setup gate.** A job can only be scored once it is *ready*: it has posting text (`jobs.description`) and a person has confirmed its scoring criteria (`jobs.criteria_confirmed_at`), per the pure `scoring/job-readiness.ts`. Saving criteria confirms them; so does the "Confirm criteria" button (`PATCH /api/jobs/:id { criteriaConfirmed: true }`); resetting to defaults does not undo it. Jobs already in use (custom criteria, or scored applicants) are marked confirmed by a one-time startup migration (`confirmCriteriaOfJobsInUse`), so existing work is never blocked; a brand-new job (first ingested by sync, posting auto-filled) stays unconfirmed. `POST /api/score` and `POST /api/score/rescore` return **409** with a plain-language message for a job that is not ready; the web UI also disables the buttons and shows a checklist banner that opens Job settings. `JobSummary`/`JobDetail` carry `hasPosting`, `isCriteriaConfirmed`, `isReadyToScore`. The MCP/skill path is not gated (a person driving Claude Code themselves).

**AI criteria suggestions.** Job settings can draft criteria two ways, both through `RubricGeneratorService` and `ClaudeRunner` (one `claude -p --output-format json` call in an empty temp folder, same signed-in Claude Code as scoring; `SCORING_MODEL` applies; still no API key in the app): *Generate from job description* (`POST /api/jobs/:id/criteria/suggest`, no body) and *Help me generate criteria* (`POST /api/jobs/:id/criteria/questions` returns 3 to 5 role-specific multiple-choice questions, falling back to a general set if the reply is unusable; the browser then sends `{ answers }` to `/criteria/suggest`, where the UI offers an "Other" free-text answer for each). Suggestions are **drafts only**: `parseCriteriaResponse` validates them (weights that are close but off are rescaled to exactly 100), the editor applies them without saving, and Undo restores the previous areas. Red flags are never generated. One generation runs at a time (409 otherwise); a retry is made once if a reply cannot be read; closing the browser aborts the run. `EXAMPLE_CRITERIA` in `scoring/rubric-generation.ts` is the example shown to the model.

**Job posting store:** BambooHR's authenticated `/applicant_tracking/jobs` exposes job metadata + a public `posting_url` but no posting body text. The public careers site does serve it as JSON (`https://<subdomain>.bamboohr.com/careers/<jobId>/detail`, HTML description), which `job-posting-fetcher.ts` converts to plain text: sync auto-fills `jobs.description` for jobs first seen in that sync (only if empty, so edits are never overwritten; closed jobs 404 and are skipped), and `POST /api/jobs/:id/import-posting` returns the text unsaved for the editor to review. `BambooHRSyncService.syncJobs()` auto-captures `posting_url`/`posted_date`/`status`/`title` into existing job rows (`JobsRepository.updateMetadata`, update-only). The posting **text** (`jobs.description`) and the per-job rubric (`jobs.system_prompt`) are both writable from the web UI (`PATCH /api/jobs/:id` → `saveJobPosting`/`saveSystemPrompt`) and, for the posting, the `save_job_posting` MCP tool. `getJobDescription` is DB-first, falling back to the legacy `server/data/job-descriptions/*.txt` files. `JobsRepository.upsert`/`updateMetadata` only touch metadata columns (and use `COALESCE`), so a sync never wipes `description` or `system_prompt`.

### MCP server (`server/src/mcp/`)

- `index.ts` (stdio entry) imports `stdio-logging.ts` **first** to reroute `console.log`/`info`/`debug` to stderr — stdout is the JSON-RPC channel and the ingest/repository code is chatty. Then it inits the DB and connects `StdioServerTransport`.
- `server.ts` builds the `McpServer` and registers tools/prompt with injected services (`deps.ts` holds the `McpDeps` bundle). Tools are grouped: `tools/read.tools.ts`, `tools/write.tools.ts`, `tools/ingest.tools.ts`; prompt in `prompts/`.
- Tool schemas use `zod`. Results go through `result.ts` (`jsonResult`/`textResult`/`errorResult`).

### Storage is split between SQLite and disk (non-obvious)

Not everything called a "repository" is database-backed.

- **SQLite** (`server/data/hiring-helper.db`; schema reference in `server/src/db/schema.sql`, built by the versioned migrations in `server/src/db/migrations/`): `jobs`, `applicants`, `applications`, `application_states`, `application_scores` (the confidence **integer only**), `content_updates`. Backed by `applications/applicants/jobs/scores/application-states/content-updates` repositories.
- **Disk JSON caches** under `server/data/cache/application/`: `summary/<applicationId>.json` (the full AI summary object) and `resume/<resumeFileId>.json` (parsed resume). `ApplicationSummaryRepository` and `ResumeRepository` are file-backed despite the "repository" name.
- So a candidate's confidence number lives in SQLite while the summary prose lives on disk. `server/data/scores.json` is a legacy pre-2.0 artifact; the app reads scores from the `application_scores` table, not this file.

### Status model

Application status is normalized: `applications.status_id` is a FK into the `application_states` table, resolved to a label via `ApplicationStatesRepository`. Both `applications` and `application_states` carry an `active` flag. `server/src/db/schema.sql` is the source of truth for the schema. The local `application_states.id` **is** BambooHR's status id (sync stores BambooHR's `status.id` as the PK via `getOrCreateByStatus`), so a status is portable between the two systems without a mapping table.

### Status write-back to BambooHR (`bamboo-push.service.ts`)

Triage is normally local-only, but locally-decided status changes can be pushed back to BambooHR on demand. `applications.bamboo_status_id` records the status BambooHR last reported; the working `status_id` is what local triage edits. A row where `status_id <> bamboo_status_id` is **pending a push** (`ApplicationsRepository.findPendingStatusPushes`).

- **Sync protection:** the sync `upsert` always sets `bamboo_status_id = excluded.status_id`, but only advances `status_id` when it wasn't locally diverged (`status_id = CASE WHEN status_id IS bamboo_status_id THEN excluded.status_id ELSE status_id END`). So an un-pushed local edit survives a sync; BambooHR's truth is still tracked. New DBs auto-migrate the column and backfill `bamboo_status_id = status_id` (`database.ts` `runMigrations`).
- **Push:** `BambooPushService.pushStatuses` calls `BambooHRService.updateApplicationStatus` (the ONLY BambooHR write) per pending row, then `markStatusPushed(id, pushedStatus)` to reconcile. Sequential + 429-aware (halts with partial progress, logs `rate_limited`). Rejection "reason" is just the rejection status; no separate reason field.
- **Never emails candidates:** `updateApplicationStatus` sends `{ status }` only; BambooHR's status endpoint has no notification param. No email/disposition endpoint is called anywhere. Do not add one.
- Local-wins on a two-sided conflict (both local and BambooHR changed); the from→to preview surfaces it. Web UI + REST only — no MCP tool.

### API surface

- `GET /api/applicants` list, with `statusIds` (comma-separated), `jobId`, `search`, `page`, `limit` (capped at 50), `sortBy`, `sortDirection`, `active`.
- `GET /api/applicants/statuses`, `GET /api/applicants/:id`, `GET /api/applicants/:id/resume`.
- `GET /api/jobs` — jobs with counts + latest activity (drives the web job selector).
- `GET /api/jobs/:id` — a job's editable config: description + effective `scoringConfig` (+ `scoringConfigIsCustom`, `isLegacyPromptActive`); `PATCH /api/jobs/:id` (`{ description?, postingUrl?, scoringConfig?, resetScoringConfig? }`) saves it. An invalid `scoringConfig` (for example points not totalling 100) is rejected with a 400 before anything is saved; `resetScoringConfig: true` returns the job to the defaults. Local only.
- `POST /api/score` (`{ jobId? }`) scores a job's **unscored** candidates via a headless-Claude-Code run; `GET /api/score/status` polls it. `POST /api/score/rescore/preview` and `POST /api/score/rescore` (`{ jobId, statusIds?, search?, active? }`) **re-score every candidate matching the active list filter** (overwriting scores, using the job's current rubric) — preview returns a count, then the run reuses the same runner/status. Scoring itself still happens through the MCP `save_evaluation` tool.
- `POST /api/applicants/bulk-preview | bulk-reject | bulk-move` — job-scoped bulk actions by a Match/Applied-Date condition; reject/move update the **local** `status_id` only (they do not push to BambooHR; use the push endpoints for that). Registered before `/:id`.
- `POST /api/applicants/push/discard` (body `{ jobId?, ids? }`) — roll pending local changes back instead of sending them: each applicant returns to `bamboo_status_id` (local only, never calls BambooHR; pending changes whose BambooHR stage is unknown are skipped). The Send to BambooHR modal offers Roll back per change and Roll back all.
- `GET /api/applicants/push/preview?jobId=` (read-only pending list) and `POST /api/applicants/push` (body `{ jobId?, ids? }`) — push local status changes back to BambooHR (status only, never emails). Registered before `/:id`.
- `PATCH /api/applicants/:id/status` — move a single applicant to a stage (local).
- `POST /api/applicants/bulk-restore` (`{ entries: [{ id, statusId }] }`) — undo a bulk reject/move/duplicate cleanup using the `previousStatuses` those endpoints return (local only). Registered before `/:id`.
- `POST /api/score/cancel` — stop the running scoring run (saved scores are kept). `ScoringStatus` also carries `total` (what the run set out to score) and `cancelled`, which drive the progress bar.
- `GET /api/setup/status`, `POST /api/setup/bamboohr/test`, `POST /api/setup/bamboohr` — first-run setup (see Config below). `POST /api/jobs/:id/criteria/questions` and `POST /api/jobs/:id/criteria/suggest` (`{ answers? }`) draft scoring criteria with Claude (see AI criteria suggestions; nothing is saved). `POST /api/jobs/:id/import-posting` returns a job's public posting text, unsaved.
- `POST /api/sync`, `GET /api/sync/status`, `GET /api/sync/history`.
- `GET /api/update/status[?refresh=1]` (version, whether a newer one exists, update progress) and `POST /api/update/apply` (managed installs only; see Installers, the `hiring-helper` command and updates).

## Client UX conventions

- The app gates on `/api/setup/status`: until BambooHR is connected, `App.tsx` redirects every route to `/setup` (`SetupScreen`); once connected, `/setup` reopens it to change credentials. The top-bar **Help** button opens `HelpOverlay`: a dimmed spotlight over the current page (applicant list or applicant detail): numbered badges on the highlighted controls, explained in one legend card. Elements opt in with `data-help="<id>"`, the id-to-text list lives in `HelpOverlay.tsx`, and the legend's position (bottom center, or top center if that hides fewer highlights) and column count is the pure `utils/helpOverlayLayout.ts`. To document a new control, add the attribute and a step.
- The page header holds **Sync with BambooHR** and `SyncStatus` (last sync, warns on failed/rate-limited). One action bar under the filters holds `ScoringControls` (Score new applicants with the unscored count, Re-score, progress/cancel), the `BulkActions` dropdown, and **Send to BambooHR** (shown only while changes are waiting, filled amber with a count; sending requires an explicit checkbox confirmation). Scoring confirmations/progress span the full row (`.action-panel`); the bulk reject/move/duplicate/send forms and Job settings each open in a `Modal` (a bulk reject/move/cleanup closes the window on success and leaves an Undo banner on the page). `Modal` uses the shared `useDialogBehavior` (Escape, focus trap, focus restore) and has a `size="wide"` option; Job settings uses it, and its criteria editor has a left menu (Evaluation framework, Red flags) that shows one section at a time and flags an invalid points total in the menu.
- Bulk reject defaults to "Match is less than 50" (move defaults to "greater than"), so the first thing shown targets the weakest candidates (`defaultOperator` in `BulkActions.tsx`).
- Bulk reject/move/duplicate cleanup keep the last action's `previousStatuses` for an Undo button (`BulkActions`). Undo is client-held only: it is lost on reload.
- Each list row ends in a "⋮" menu (`RowActionsMenu`, rendered in a portal because the table clips overflow), in three groups separated by dividers: **Move to stage, Reject** (change the applicant; `RowActionModal` makes a single local status change with an Undo notice via `bulk-restore`; **Notes** opens the candidate's notes in BambooHR in a new tab, so notes live in BambooHR and are not stored here), **View résumé** (the `ResumeModal`, stepping through the page's applicants with a `StageMover` footer) and **View profile**, then **Copy applicant link**. Both use `utils/bamboohrLinks.ts`: `https://<subdomain>.bamboohr.com/hiring/candidates/<candidateId>` (Notes appends `#ats-notes`), where `candidateId` is `applicants.id` (BambooHR's `applicant.id`, exposed on list items as `applicantId`), NOT the application id. The route shape was confirmed by probing the tenant unauthenticated; if a link ever opens the wrong person, the id choice is the thing to revisit and **Copy email**. Menu clicks must stop propagation (React events bubble through portals) or they would also open the row.
- Status filters are remembered **per job** (`filterStorage.ts`); `ViewsMenu` offers built-in views from the status groups plus user-saved views (`savedViews.ts`, localStorage).
- The résumé viewer (`ResumeModal`) steps through the applicants last shown in the list (`applicantNavigation.ts`, sessionStorage) and hosts a `StageMover` footer with a one-click "Not a Fit".
- Pure client helpers have tests: `npm run test --workspace=client` (Node's runner via tsx, like the server; `*.test.ts` are excluded from the client `tsc` build). There is still no component test setup.

## Conventions and gotchas

- **ESM `.js` import extensions.** The server is ESM (`"type": "module"`, `moduleResolution: node`). Relative imports must end in `.js` even though the source is `.ts` (e.g. `import { getDatabase } from '../db/database.js'`). Match the existing pattern or the build/runtime breaks.
- **DB is a singleton initialized at startup.** `getDatabase()` throws if `initializeDatabase()` has not run. `initializeDatabase()` runs the **versioned migrations** (`server/src/db/migrator.ts`, `migrations/`): the schema version lives in `PRAGMA user_version`, each pending migration runs once in its own transaction, a copy of an existing database is written to `server/data/backups/` first (gitignored; newest 3 kept), and a database from a newer app is refused. A new database replays every migration from 0, so there is no separate "fresh" path. To change the schema add a numbered migration (never edit a shipped one), update `schema.sql` (a test fails if it disagrees with the migrations), and add a test; see DATABASE.md. Per-boot self-healing that is not tied to a version lives in `repairData`. The old `scripts/add-*-migration.ts` files are superseded.
- **Repository pattern.** DB columns are `snake_case`; domain objects are `camelCase`. Each DB repository has a private `get db()` accessor and a private `rowToX` mapper. `better-sqlite3` is synchronous; some repositories (`ScoresRepository`, the file-cache ones) still wrap calls in `async` to keep a uniform interface.
- **Route ordering matters.** Static routes like `/api/applicants/statuses` are registered before `/:id` so the param route does not swallow them. Keep new static routes above param routes.
- **Loopback only.** The REST server binds to `127.0.0.1` (`LOOPBACK_HOST` in `server/src/index.ts`) and the Vite dev server to `127.0.0.1` (`client/vite.config.ts`), because the API has no auth and serves applicant PII. Don't bind to `0.0.0.0` without adding authentication. `localOnlyGuard` (`middleware/local-only.middleware.ts`) also refuses any request whose `Host` is not `localhost`/`127.0.0.1`/`[::1]` (DNS rebinding) and any write (POST/PATCH/DELETE) whose `Origin` is not local (cross-site requests); requests with no `Origin` (curl, scripts) are allowed.
- **Rate limiting skips GET.** `express-rate-limit` is applied to `/api/applicants` and `/api/sync` but skips GET requests, so read endpoints stay responsive. Only mutating/expensive POSTs are limited.
- **Two processes, one DB.** The REST server and the MCP server both open `server/data/hiring-helper.db`. `initializeDatabase()` sets `journal_mode = WAL` so concurrent access does not throw `SQLITE_BUSY`.
- **Config.** A single root `.env` is loaded by `server/src/config/env.config.ts` via a relative path. `BAMBOOHR_API_KEY` and `BAMBOOHR_SUBDOMAIN` are needed for sync, but the server no longer throws without them: it starts, skips the initial sync, and the web app shows a first-run setup screen (`/api/setup/status`, `GET /api/setup/bamboohr/connection` (tests the SAVED key, cached 60s server-side and dropped when credentials change, never returns the key), `POST /api/setup/bamboohr/test`, `POST /api/setup/bamboohr`) that tests the credentials, writes them to `.env` (`SetupService`, `utils/env-file.ts`), applies them in memory and starts the first sync. `BambooHRService` builds its axios client lazily so new credentials take effect without a restart, and throws `BambooHRNotConfiguredError` until then. No LLM provider keys are used.
- Formatting follows `.prettierrc.json` (single quotes, semicolons, 100 col width, 2-space indent, trailing commas es5). The server tsconfig is strict with `noUnusedLocals`/`noUnusedParameters`/`noImplicitReturns`.
